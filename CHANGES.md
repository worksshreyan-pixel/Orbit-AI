# 2026-09-15 — Local Agent WebSocket Authentication Fix

## 1. What changed?
Fixed a critical bug that was preventing the ORBIT web application from successfully authenticating with the Local Agent running on your computer. The ORBIT app now automatically reads the exact secure credential generated by the Local Agent, instead of requiring you to manually copy and paste it into an environment file.

## 2. Why was it needed?
During the initial pairing process, the ORBIT server would verify the 6-digit code and generate a secure, 64-character token. The Local Agent successfully received this token and stored it securely. However, the ORBIT web application did not store this token. It expected the token to be manually placed in a `.env.local` file under `LOCAL_AGENT_CREDENTIAL`. When the 6-digit code was mistakenly placed there instead of the full token, the authentication failed, blocking ORBIT from communicating with the Local Agent.

## 3. What was happening before?
ORBIT tried to connect to the Local Agent's WebSocket server and sent the `LOCAL_AGENT_CREDENTIAL` from the `.env.local` file. Because this was just the 6-digit code (e.g., `808564`), the Local Agent rejected it because it expected the full 64-character token (e.g., `b3a10343...`). The connection was terminated immediately.

## 4. What happens now?
When ORBIT runs locally on your computer, it now automatically checks a secure location on your hard drive (`%APPDATA%\orbit\local-agent\credential.json`) to find the exact token the Local Agent is using. It uses this exact token to authenticate. You no longer need to manually manage the `LOCAL_AGENT_CREDENTIAL` in your environment file.

## 5. How does it work?
1. A new file `local-credentials.ts` was created. It contains a helper function `getLocalCredential()`.
2. This function looks for the `LOCAL_AGENT_CREDENTIAL` in the environment. If it's not a valid 64-character token, it falls back to reading the `credential.json` file directly from the Windows `%APPDATA%` directory.
3. The ORBIT connection managers (`computer.ts`, `command.ts`, and `proactive.ts`) were updated to use this helper function.
4. When ORBIT opens the WebSocket connection to the Local Agent, it sends the correct token.
5. We also added diagnostic logging that prints a "fingerprint" (a short, hashed version of the token) so we can see they match without exposing the actual secret.

## 6. Technology involved
- **WebSocket**: A protocol that allows two-way, persistent communication between a client (ORBIT) and a server (Local Agent). Unlike standard HTTP where the client has to keep asking for updates, WebSockets stay open so the agent can stream data (like active windows) in real time.
- **Environment Variables (.env)**: Files used to store configuration and secrets outside of the source code.
- **%APPDATA%**: A hidden folder on Windows (usually `C:\Users\YourName\AppData\Roaming`) where applications store user-specific data and settings securely.
- **Tokens**: Long, random strings of characters used like digital keys. They are mathematically impossible to guess, making them secure for authentication.
- **SHA-256 Fingerprint**: A cryptographic method that scrambles a secret into a fixed-length string. We use the first 8 characters of this scrambled string to verify that two secrets are identical without ever revealing the secrets themselves.

## 7. Files changed
- `lib/agent/providers/local-credentials.ts`: **[NEW]** Contains the logic to find and read the Local Agent's `credential.json` file.
- `lib/agent/providers/computer.ts`: **[MODIFIED]** Updated to use the new credential helper instead of relying solely on the `.env.local` file.
- `lib/agent/providers/command.ts`: **[MODIFIED]** Updated to use the new credential helper for terminal commands.
- `lib/notifications/proactive.ts`: **[MODIFIED]** Updated to use the new credential helper for proactive desktop notifications.
- `local-agent/src/server.ts`: **[MODIFIED]** Added diagnostic fingerprint logging to the Local Agent WebSocket server to help debug future authentication issues.

## 8. Architecture impact
This change solidifies ORBIT's "local-first" single-tenant architecture for desktop interactions. Instead of routing credentials through a cloud database (which would require complex synchronization), ORBIT embraces the fact that it runs on the same physical machine as the Local Agent, leveraging direct file-system access for secure, instant credential sharing.

```text
ORBIT (Next.js) 
  |
  |--- Reads credential from ---> [ %APPDATA%\orbit\local-agent\credential.json ]
  |                                       ^
  |--- Connects with credential           | Writes credential during pairing
  v                                       |
Local Agent (WebSocket Server on port 3001)
  |
  v
Windows OS (Executes commands, gets active window, etc.)
```

## 9. Important technical decisions
- **Why read the file directly instead of updating the database?** Adding the credential to the Supabase database would have required a database migration and added complexity for local development. Since ORBIT runs locally on your machine during development, reading the file directly is the most robust, zero-configuration approach.
- **Why fingerprinting?** Logging the raw token would be a massive security vulnerability. By hashing the token and logging only the first 8 characters, we can visually confirm both sides have the exact same token without exposing it to log files or AI models.

## 10. Bugs/problems encountered
- **ts-node compatibility**: When trying to write a quick test script to verify the connection, `ts-node` struggled with modern ES Modules (import statements). I bypassed this by using `tsx`, a more modern TypeScript executor, which seamlessly ran the test script.

## 11. Testing
- **Local Agent Build passed**: Successfully compiled the TypeScript Local Agent.
- **Unit tests passed**: Ran the Jest test suite (`__tests__/agent/computer-provider.test.ts`), which successfully connected to the running WebSocket server.
- **Live/manual test passed**: Created a manual script (`test-ws.ts`) that successfully invoked the `get_active_window` capability end-to-end, returning the expected Windows process name.

## 12. Security considerations
- The actual 64-character token is strictly protected. It is never logged.
- The `credential.json` file is stored in `%APPDATA%`, which is restricted to your Windows user account.
- The fallback logic first checks the environment variable, maintaining compatibility with potential future cloud deployments where `%APPDATA%` wouldn't be available.

## 13. What I should learn from this
- **Environment variables vs. File storage**: Sometimes, storing configuration in a file is better than an environment variable, especially if a background process (like the Local Agent) needs to rotate or update that configuration dynamically.
- **WebSockets for Agents**: WebSockets are the backbone of how AI agents interact with your computer in real-time, because they allow the agent to continuously monitor things without having to establish a new connection every second.
- **Debugging with Fingerprints**: You can compare two secrets safely by hashing them. If the hashes match, the secrets match.
